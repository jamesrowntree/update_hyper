Incremental update — append new rows from a .hyper payload file

Two standalone code examples that append brand-new rows to a Tableau .hyper extract with data from a separate .hyper data source.

Client-side append — incremental_update.py runs locally: a Hyper engine process on your machine attaches the extract and a payload file, then appends with one INSERT INTO ... SELECT *. No network calls.

Server-side append — update_cloud_hyper_data.py pushes data pieces/shards straight to an already-published Tableau Cloud data source and lets Cloud do the appending/unioning, instead of unioning locally first. Particularly useful once the extract you're adding to is already published and getting too large to republish in one shot: it lets you append pieces directly to your published data source, rather than re-publishing the whole dataset.

Client-side append (local, engine-side): incremental_update.py

Everything in this section runs entirely on your machine — nothing here talks to Tableau Cloud. See Server-side append below for the alternative that appends directly to an already-published Cloud data source.

Requirements

The project virtualenv with tableauhyperapi installed (see the main README.md §Setup for setup). The commands below are run from the project root (the parent of scripts/):

source .venv/bin/activate

Running it

python3 scripts/generate_new_rows.py       # Create the new rows / payload (data/New_Rows.hyper)
python3 scripts/incremental_update.py      # append the payload to a disposable copy

How it works

  1. generate_new_rows.py opens the real extract read-only to copy its Extract table definition, creates an identically-shaped "public"."New_Rows" table in New_Rows.hyper (CreateMode.CREATE_AND_REPLACE, fresh every run), and bulk-inserts the NEW_ROWS list with an Inserter.
  2. incremental_update.py copies the extract to a throwaway file, then opens a single Hyper connection and attaches both files under aliases — target (the copy) and newrows (the payload) — so one SQL engine sees both, addressable as "alias"."schema"."table".
  3. It appends everything in one statement: 
    INSERT INTO "target"."public"."Extract"
SELECT * FROM "newrows"."public"."New_Rows"
    Because New_Rows has exactly the same column shape as Extract, SELECT * lines up 1:1, and the read + append happen natively inside Hyper — the Python layer only issues the command string.

Why attach both files (rather than open the copy directly)?

Only because we're using Hyper for our source file. Opening a connection directly against one .hyper file and then attaching a second changes how the unqualified "public"."Extract" name resolves, and the statement fails with schema "public" does not exist. Attaching both under explicit aliases and using fully-qualified three-part names avoids the ambiguity — and matches how update_existing_rows.py, union_hyper_files.py and generate_split_by_year.py already work.

Sourcing the new rows from somewhere else (eg Snowflake)

The append step is deliberately source-agnostic: incremental_update.py only ever reads the attached New_Rows.hyper, so it never changes regardless of where the rows originally came from. The Hyper engine can't attach or query Snowflake directly, so if your new rows live in Snowflake the swap point is generate_new_rows.py, not the append script. See the Snowflake block in that file for two ready-to-adapt approaches:

  • Python connector (snowflake-connector-python): run a SELECT, fetchall(), and feed the rows to the same Inserter in place of the hardcoded list.
  • Bulk via Parquet: COPY INTO a stage as Parquet in Snowflake, then let the Hyper engine read it with COPY ... FROM ... WITH (FORMAT parquet).

Customising the payload

Editing which rows get appended is a data-only change — no edits to incremental_update.py:

  1. Edit the NEW_ROWS list in generate_new_rows.py (or point it at Snowflake, as above). Each row must be in the extract's 21-column order.
  2. Re-run python3 scripts/generate_new_rows.py, then python3 scripts/incremental_update.py.

Publishing the result to Tableau Cloud

incremental_update.py only ever writes to the disposable Example_Insert.hyper copy — nothing it does reaches Tableau Cloud. To make the appended rows show up in a published data source, publish that copy with publish_to_tableau_cloud.py (the core pipeline's publish step; see readme_Union.html for the full reference): 

# Publish the copy with the appended rows, updating the existing "Finished Merged" data source in place
python3 scripts/publish_to_tableau_cloud.py --source=data/Example_Insert.hyper --target="Finished Merged"

If the target data source already exists, its model is preserved — the .tds is edited in place and only the extract data is swapped, so calculated fields, folders and aliases already on the data source survive.

--metadata is optional, and metadata is only applied if you pass it. Run publish_to_tableau_cloud.py without --metadata and the publish updates the extract data only — no description, certification, tags, column descriptions, or calculated fields are touched. To also refresh those, regenerate the metadata JSON from the appended copy and pass it explicitly: 
python3 scripts/generate_metadata.py --source=data/Example_Insert.hyper --output=data/datasource_metadata.json
python3 scripts/publish_to_tableau_cloud.py --source=data/Example_Insert.hyper --target="Finished Merged" --metadata=data/datasource_metadata.json
generate_metadata.py preserves any hand-added calculations block already in --output when it re-profiles, so regenerating won't wipe calculated fields you've added to the metadata JSON. Add --dry-run to either command to preview without making a network call.

Safety

Finished_Merged.hyper (and the live Tableau Cloud data source it backs) is never touched by incremental_update.py or generate_new_rows.py — every run works on a fresh Example_Insert.hyper copy, so both are safe to re-run any number of times. Publishing that copy with publish_to_tableau_cloud.py (above) is the one step in this section that does make a live change on Tableau Cloud.

Server-side append (Tableau Cloud): update_cloud_hyper_data.py

incremental_update.py (above) appends rows locally: it opens a Hyper engine process on your machine, attaches two files, and writes the result to a new local .hyper file that would then need to be (re)published as a whole. update_cloud_hyper_data.py takes the opposite approach: it pushes individual .hyper “piece” files straight to an already-published Tableau Cloud data source over the REST “Update Data in Hyper” API (tableauserverclient's datasources.update_hyper_data), and lets Cloud append/union them into the live extract, one piece at a time — no local union, and no full republish.

Why this exists: a single publish (publish_to_tableau_cloud.py) is bounded in size. Once the locally-unioned extract (Finished_Merged.hyper) gets large, republishing it whole can hit that ceiling. Growing the already-published data source piece by piece sidesteps that — each upload only has to clear the much smaller per-piece ceiling, not the size of the whole data source.

A “piece” here plays the same role New_Rows.hyper plays for incremental_update.py: an externalised payload with the same table shape as the target ("public"."Extract", e.g. one Start_<year>.hyper file per season, as produced by generate_split_by_year.py) — except here each piece is read and merged by Tableau Cloud, not by a local Hyper process.

How the pieces/shards are staged on Cloud before they're unioned

This is the part that differs most from the client-side section above, where everything happens inside one local Hyper engine call. For each piece, the script issues a separate update_hyper_data request (a fresh request_id, one insert or replace action) and then blocks on server.jobs.wait_for_job(...) before moving on to the next piece — pieces are uploaded and committed one at a time, sequentially, never all at once:

  1. The piece file is uploaded to Tableau Cloud as the payload of that one request. This upload is transient staging state, scoped to the background job that will process it — it is not a browsable file, not a new revision, and not a permanent object anywhere on the site. There's no place in the Cloud UI where an in-flight piece is visible.
  2. A background job then applies the requested action directly to the data source's real, already- persisted extract table:
    • insert — the piece's rows are appended to the existing target table, equivalent to a server-side INSERT INTO ... SELECT *.
    • replace — the target table is cleared first, then loaded from the piece — equivalent to a server-side truncate-then-load.
  3. Once the job reports success, the staged piece is discarded. Nothing about it lingers on Cloud afterwards — only its rows, now merged into the target extract's persisted data, remain.

Because each piece is fully committed before the next one is even uploaded, there is never a point where Cloud is holding several pending pieces side by side waiting to be unioned together in one batch. The eventual “union” of all your pieces is really the cumulative effect of a sequence of small server-side inserts, built up job by job — not one atomic UNION ALL the way union_hyper_files.py does it locally. --mode reload makes this concrete: piece 1 goes in via replace (the target table now holds just piece 1's rows), then every remaining piece goes in via insert, growing the target table one piece at a time until it holds the union of all of them.

If a multi-piece --mode reload run is interrupted partway through, whichever pieces already committed are already merged into the live target table — there is no single rollback point covering the whole run. Re-running the same --mode reload command is safe (it starts over with replace on the first piece), but a failed run does not mean nothing changed on Cloud.

Modes

ModeBehaviour
--mode append Insert the given pieces into the existing data source, leaving its current rows in place. For incremental loads (e.g. one new season's file). Re-sending the same piece duplicates its rows — send each piece exactly once. Fails if the data source doesn't exist yet.
--mode reload Rebuilds the whole data source from the given pieces: the first piece via replace (clears the target table), every remaining piece via insert. If the target data source doesn't exist yet, it's created by publishing the first piece, then the rest are inserted.

Safeguards

  • Per-piece size ceiling. Each upload is bounded by the Cloud setting api.server.update_uploaded_file.max_size_in_mb (default 100 MB, fixed on Cloud — chunked upload cannot make one update exceed it), even though the aggregate data source may end up far larger. A pre-flight check reports every piece's size and aborts before any upload if one is at/over the limit, so a doomed run never half-loads the target.
  • Defaults to a separate test data source. --datasource-name defaults to "Finished Merged (API Union Test)", not the real Finished Merged data source, so you can validate the approach without risking live content. Point it at the real data source with --datasource-name "Finished Merged" only once you're happy.
  • Model preserved. update_hyper_data changes data only, so calculated fields, column descriptions, folders and aliases already on the data source survive untouched — no .tds download/patch/rebuild, unlike publish_to_tableau_cloud.py. The one exception is the create path: a brand-new data source published from a bare piece only has the fields present in that piece's extract.
  • Table-name mismatch is expected. Piece files carry table "public"."Extract", but a data source published from such a .hyper commonly stores its extract as "Extract"."Extract" on Cloud. --source-schema/--source-table and --target-schema/--target-table are configurable if an update fails complaining about an unknown table.
  • Always logged. Every run writes a full, timestamped record to logs/update_<timestamp>.log; --silent suppresses console output only, never the log file.

Requirements

Unlike incremental_update.py (fully local), this script makes real network calls to Tableau Cloud, so it needs a filled-in .env — the same configuration as publish_to_tableau_cloud.py — see the main README.md §Setup.

Running it / Usage

# Build the whole test data source from all yearly pieces server-side (creates it if it doesn't exist)
python3 scripts/update_cloud_hyper_data.py --mode reload

# Append just the new season's piece to it
python3 scripts/update_cloud_hyper_data.py --mode append --files data/Start_2026.hyper

# See the plan + per-piece size report without calling Cloud
python3 scripts/update_cloud_hyper_data.py --mode reload --dry-run

# Push to a specific data source (e.g. the real one, once validated)
python3 scripts/update_cloud_hyper_data.py --mode reload --datasource-name "Finished Merged"

Safety

update_cloud_hyper_data.py targets a separate test data source by default (see Safeguards above) and always writes a full log under logs/. But once pointed at a real data source it does make live changes on Tableau Cloud — a piece pushed with --mode append is not undone by re-running the script, and --mode reload's first piece clears the target table via replace before reloading it.
